## Locked Decisions (context for all prompts)

- Messaging: **MassTransit v8** (stay OSS; v9 is commercial) + **RabbitMQ** transport
- Saga persistence: **PostgreSQL + EF Core** saga repository, added to Aspire AppHost via `AddPostgres`, optimistic concurrency
- Approval gate: `POST /api/approvals/{id}/approve` and `/reject` on AgentHost; approval state lives in the saga; agent replies "pending approval, ref #X"; no UI
- Notification Service: minimal Node/TS RabbitMQ consumer that logs simulated emails — nothing more
- Eval harness: console project `NexusOps.Evaluation`, JSON dataset of 20–30 prompts, asserts correct tool selection and direct-vs-saga routing; it MUST support credential-free dataset validation separately from live model evaluation
- `NexusOps.Server` + `frontend/` remain scaffold reference artifacts; no frontend work
- Testing: one Aspire.Hosting.Testing integration test per saga, minimum
- Local orchestration uses `dotnet run --project NexusOps.AppHost` for both delegated agent sessions and the documented human quickstart — the local `aspire` CLI (13.2.1) doesn't work against this project's Aspire package version (13.5.3, see Prompt 3's completion note below), so `aspire start`/`aspire describe` are not viable here; no deployment
- Azure AI credentials are available locally. Build, unit, saga, approval, and Aspire integration tests MUST NOT require them (CI runs credential-free). Live chat and model-based evaluation MUST skip with a clear message when credentials are absent so CI never needs them, but they are expected to pass in local runs where credentials are present.
- When MassTransit is introduced, pin all `MassTransit*` packages to v8.x and add a Dependabot major-version ignore rule; v9 is commercial and out of scope.
- Resume framing: fintech ops → agentic workflows (investigation fan-out ≈ upstream aggregation; approval gate ≈ maker-checker; compensation ≈ reversing partial writes; curated tools ≈ governed API surface)

**Docker became available mid-session and the suite was live-run to completion.** First run (parallelism bug present): 2/4 passed, 2/4 failed with `RequestTimeoutException` on both investigation tests. Diagnosed via the Postgres SQL trace, not guessed: fixed the test-authoring parallelism bug and a wrong `KnownResourceStates.Exited` wait (a stopped **project** resource doesn't necessarily land there; switched to `KnownResourceStates.TerminalStates`) — re-ran, and the *same two investigation tests still failed identically*, now demonstrably independent of any test-side bug. Root cause: a real, 100%-reproducible race in `OrderInvestigationSaga` itself (feature 005) — its `Initially(When(Requested))` publishes `BeginInvestigationFanOut` before its own row-creating `INSERT` commits, so the fan-out consumer's (structurally fastest) `OrderFindingReported` reply reliably raced ahead of the saga's own commit and was silently discarded, hanging the investigation forever. This was fixed as its own spec-kit feature, `specs/008-order-investigation-outbox/` (full specify → clarify → plan → tasks → implement → analyze workflow, on branch `008-order-investigation-outbox`): the same transactional-EF-outbox treatment `OrderActionSaga` already has (feature 006) for the identical class of problem, applied to `OrderInvestigationSaga`. One genuine implementation wrinkle surfaced along the way and is documented in that spec's `research.md` Decision 4: a *private* copy of the outbox tables for `OrderInvestigationDbContext` (tried as a renamed table, then a renamed schema) does not work with this version of MassTransit's Postgres outbox — its row-lock query hardcodes an unqualified table reference regardless of the entity's actual mapping — so the fix instead shares `OrderActionDbContext`'s existing `InboxState`/`OutboxState`/`OutboxMessage` tables (safe: MassTransit's own `(MessageId, ConsumerId)` dedup key already partitions rows correctly per receive endpoint).

A code-review pass after the first green run found several real issues, all fixed and re-verified against real infrastructure: (1) the outbox migration's `Up()` was a bare no-op assuming `OrderActionDbContext`'s migration would always run and create the shared tables first — rewritten as `CREATE TABLE/INDEX IF NOT EXISTS`, self-healing if `OrderAction` is ever deleted (this project's own documented removal story) or its migration rolled back, and `Program.cs` now runs `OrderActionDbContext`'s migration before `OrderInvestigationDbContext`'s so the (non-idempotent) original migration still creates the tables normally today; (2) `WorkflowOrchestratorFixture` now strips `WithDataVolume()`'s mount from `postgres`/`rabbitmq` before building, since that volume's name is derived from the AppHost project itself and would otherwise collide with a developer's own `dotnet run --project NexusOps.AppHost`; (3) `InitializeAsync` is now wrapped in try/catch that disposes whatever was started before rethrowing, since xUnit v2 doesn't reliably call `DisposeAsync()` when `InitializeAsync()` itself throws; (4) the degraded-investigation test's `StopResourceAsync` call now lives inside its own `try`, not before it, so a timeout in the stop itself still triggers the restart; (5) `OrderInvestigationDbContext`'s outbox registration dropped the unnecessary `UseBusOutbox()` and added `DisableInboxCleanupService()`, since `OrderActionDbContext`'s own cleanup service already covers their now-shared inbox table. `frontend/package-lock.json`'s unrelated pre-existing staged diff was also reverted out of this change set.

**Final state, live-verified against real Docker-provisioned RabbitMQ and PostgreSQL**: `dotnet test NexusOps.deployable.slnf` → 174/174 unit tests (`NexusOps.Tests`, unaffected — its `OrderInvestigationSagaTests.cs` uses an in-memory harness that can't exercise this race either way); `dotnet test NexusOps.IntegrationTests` separately → 4/4 integration tests, all green, zero regression, confirmed against a freshly-wiped Docker volume state matching what a first-ever CI run would see. The previously-100%-reproducible investigation timeout is now a ~1s response. CI's new `integration-tests` job (GitHub-hosted `ubuntu-latest`, which ships Docker) will exercise this same suite on the next push to `master`.
