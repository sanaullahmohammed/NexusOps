# Implementation Plan: E-Commerce Domain Services with Direct-Path Tool Integration

**Branch**: `001-ecommerce-domain-services` | **Date**: 2026-05-28 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `specs/001-ecommerce-domain-services/spec.md`

## Summary

Add three read-only e-commerce domain services (Order, Inventory, Product), a `NexusOps.Contracts` shared library with curated tool definitions and response DTOs, and wire six `AIFunction` tool handlers into AgentHost so the agent can answer natural language read queries end-to-end via the Direct path. All services are in-memory (no persistent storage), registered in Aspire AppHost with service discovery and health checks, and emit OpenTelemetry telemetry via the shared `ServiceDefaults` pattern.

## Technical Context

**Language/Version**: C# / .NET 10

**Primary Dependencies**:
- `Microsoft.Agents.AI` 1.0.0 + `Microsoft.Agents.AI.OpenAI` 1.0.0 (tool registration via `IList<AITool>` passed to `AsAIAgent`)
- `Microsoft.Extensions.AI` (AIFunctionFactory.Create for tool handler registration)
- `Microsoft.Extensions.ServiceDiscovery` (Aspire named HttpClient resolution)
- `Aspire.AppHost.Sdk` 13.3.5 (AppHost orchestration)
- `Azure.AI.OpenAI` 2.1.0 (existing, no change)

**Storage**: In-memory static lists seeded at startup (no database)

**Testing**: `dotnet test` (xUnit); manual verification via Aspire dashboard + curl

**Target Platform**: Local development via `dotnet run --project NexusOps.AppHost`

**Performance Goals**: E2E chat response under 10 seconds (SC-001); per-service HTTP response under 200ms (internal target)

**Constraints**: No hardcoded service URLs; all HTTP calls via Aspire service discovery named clients

**Scale/Scope**: 4 new projects, 3 updated projects, ~15 new source files

**Structure Decision**: Multi-project layout with one project per domain service plus a shared Contracts library. This satisfies Constitution Principle V (domain pluggability) — services are independently swappable. Tool handlers are isolated in `AgentHost/Tools/` to keep them discoverable without polluting the existing AgentHost extension structure.

## Implementation Phases

### Phase A: Contracts Library

1. Create `NexusOps.Contracts` class library project
2. Add to `NexusOps.sln`
3. Implement `ToolNames.cs`, `SeedDataConstants.cs`, `ToolResult.cs`, and all DTO records
4. Add `NexusOps.Contracts` project reference to AgentHost, OrderService, InventoryService, ProductService

### Phase B: Domain Services (repeat pattern × 3)

For each of OrderService, InventoryService, ProductService:
1. Create ASP.NET Core Minimal API project (`dotnet new web`)
2. Add `NexusOps.Contracts` project reference
3. Call `AddServiceDefaults()` and `MapDefaultEndpoints()` in `Program.cs`
4. Implement internal Models, in-memory Store with seed data (referencing `SeedDataConstants`)
5. Implement Endpoints extension (map GET routes per contract)
6. Add project to `NexusOps.sln` and `NexusOps.deployable.slnf`

### Phase C: AppHost Wiring

1. Add project references for all three new services to `NexusOps.AppHost.csproj`
2. Update `AppHost.cs`:
   - Register `order-service`, `inventory-service`, `product-service` with `WithHttpHealthCheck("/health")`
   - Wire `agentHost.WithReference(orderService).WithReference(inventoryService).WithReference(productService)`

### Phase D: AgentHost Tool Handlers

1. Register named HttpClients in `Program.cs` with `AddServiceDiscovery()`:
   - `"order-service"`, `"inventory-service"`, `"product-service"`
2. Implement `Tools/OrderTools.cs`, `Tools/InventoryTools.cs`, `Tools/ProductTools.cs`:
   - Each handler: `IHttpClientFactory` → named client → GET call → deserialize → `ToolResult<T>`
   - Failure path: catch all exceptions → log warning → `ToolResult<T>.Fail(reason)`
3. Implement `Tools/ToolHandlerExtensions.cs` (`AddToolHandlers()`) that:
   - Registers individual tool handler classes as services
   - Builds `IList<AITool>` from `AIFunctionFactory.Create(...)` calls
   - Registers the list as a singleton `IList<AITool>`
4. Update `AgentServiceExtensions.cs` to resolve `IList<AITool>` from DI and pass to `AsAIAgent`
5. Update agent instructions in `AzureAIOptions.cs` to reference the six new tool names

### Phase E: Verification

1. `dotnet build NexusOps.deployable.slnf` — all projects build clean
2. `dotnet run --project NexusOps.AppHost` — all 5 services healthy in dashboard
3. Manual curl tests against each acceptance scenario in spec (User Stories 1–4)
4. Confirm distributed traces in Aspire telemetry dashboard per SC-005
