# Implementation Plan: Session Management

**Branch**: `002-session-management` | **Date**: 2026-05-28 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/002-session-management/spec.md`

## Summary

Add Redis-backed conversation history to `POST /api/chat` so the AI agent can reference prior turns in a conversation. Each request carries an optional `sessionId`; the server loads stored history, feeds it to the agent alongside the new user message, then saves the updated history back. Sessions expire after 30 minutes of inactivity and are permanently deleted. The chat endpoint contract is extended additively — callers that ignore `sessionId` continue to work unchanged.

## Technical Context

**Language/Version**: C# / .NET 10

**Primary Dependencies**:
- `Microsoft.Agents.AI` 1.8.0 — `AIAgent.RunAsync(IEnumerable<ChatMessage>, AgentSession, AgentRunOptions, CancellationToken)`
- `Aspire.Hosting.Redis` 13.3.5 — AppHost Redis resource provisioning
- `Aspire.StackExchange.Redis.DistributedCaching` 13.3.5 — `IDistributedCache` with OTel auto-wiring
- `System.Text.Json` (in-box) — `ConversationTurn` serialisation

**Storage**: Redis (via Aspire; `IDistributedCache` abstraction); sliding TTL 30 min; key `nexusops:session:{guid}`

**Testing**: `dotnet test` (xUnit); in-memory `IDistributedCache` stub for unit tests; integration test hitting real Redis via Aspire test container

**Target Platform**: Linux container (Aspire-orchestrated)

**Performance Goals**: Session load + save adds ≤100 ms to end-to-end chat latency (SC-003)

**Constraints**: Max 20 turns per session (configurable); graceful degradation when store is unavailable

**Scale/Scope**: Single-service change (AgentHost) + AppHost topology update

## Constitution Check

- [x] **I. Cognition/Durability boundary** — Session store lives in AgentHost (cognition layer). No saga logic introduced. The store is a cache, not a workflow.
- [x] **II. Curated tool boundaries** — No new domain tools added. Session management is infrastructure; it is invisible to the agent's tool routing.
- [x] **III. Approval-gated side effects** — Session read/write is not a real-world mutation. No approval gate required.
- [x] **IV. Message-driven service integration** — Cache access uses `IDistributedCache` (client-side library). AMQP applies to saga-to-service only; not relevant here.
- [x] **V. Domain pluggability** — `ConversationTurn` is a generic role/content DTO; no domain knowledge leaks into it. Session management works for any domain pack.
- [x] **VI. Observability first** — AgentHost already calls `AddServiceDefaults()`. Redis OTel traces auto-wired via Aspire integration. FR-012 lifecycle events explicitly emitted via `ActivitySource` or `ILogger` at key session moments.

## Implementation Phases

### Phase A — AppHost Topology

1. Add `Aspire.Hosting.Redis` package reference to `NexusOps.AppHost.csproj`
2. In `AppHost.cs`: add `builder.AddRedis("redis")` resource with `.WithDataVolume()` for dev persistence
3. Chain `.WithReference(redis).WaitFor(redis)` onto the `agentHost` builder

**Verification**: `dotnet run --project NexusOps.AppHost` — Aspire dashboard shows Redis resource healthy

### Phase B — AgentHost: Configuration + Store

1. Add `Aspire.StackExchange.Redis.DistributedCaching` to `NexusOps.AgentHost.csproj`
2. Create `Configuration/ConversationSessionOptions.cs` with `MaxTurns` (default 20) and `SlidingExpirationMinutes` (default 30)
3. Create `Services/ConversationTurn.cs` — record with `Role`, `Content`, `Timestamp`
4. Create `Services/IConversationStore.cs` — interface with three methods
5. Create `Services/RedisConversationStore.cs` — `IDistributedCache` implementation:
   - `GetHistoryAsync(sessionId)` → deserialise JSON; return empty list on miss/error
   - `AppendTurnsAsync(sessionId, newTurns, options)` → load + append + trim + serialise + save with sliding TTL; no-op on error
   - `DeleteSessionAsync(sessionId)` → `cache.RemoveAsync(key)`
6. Register in `Program.cs`:
   - `builder.AddRedisDistributedCache("redis")`
   - `builder.Services.Configure<SessionOptions>(config.GetSection("Session"))`
   - `builder.Services.AddSingleton<IConversationStore, RedisConversationStore>()`

**Verification**: Unit tests with `MemoryDistributedCache` stub — GetHistory miss, AppendTurns round-trip, trim at boundary, error suppression

### Phase C — AgentHost: Service + Endpoint

1. Update `IAgentService.cs`: `SendAsync(string prompt, string? sessionId, CancellationToken)` → returns `(string response, string sessionId)`
2. Update `AgentService.cs`:
   - If `sessionId` is null/empty → generate `Guid.NewGuid().ToString()`
   - Load history via `IConversationStore.GetHistoryAsync`
   - Map `ConversationTurn` list → `List<ChatMessage>` (role mapping: `"user"` → `ChatRole.User`, `"assistant"` → `ChatRole.Assistant`)
   - Append new user `ChatMessage`
   - Call `_agent.RunAsync(messages, session: null, options: null, cancellationToken)`
   - Extract response string
   - `AppendTurnsAsync` with user + assistant turns
   - Emit lifecycle log events (FR-012) from `AgentService`: `session.created` (Info), `session.history_loaded` (Debug), `session.history_saved` (Debug)
   - `session.degraded` (Warning) is emitted by `RedisConversationStore` directly — it has the exception context and can categorise the failure as `connection`, `timeout`, or `serialisation`
   - Return `(responseText, sessionId)`
3. Update `ChatEndpoints.cs`:
   - `ChatRequest` gains `string? SessionId`
   - `ChatResponse` gains `string SessionId`
   - Endpoint calls `agentService.SendAsync(request.Prompt, request.SessionId, ct)` and includes returned `sessionId` in response

**Verification**: Integration test — two consecutive requests sharing a session ID; second response references first exchange context

### Phase D — Configuration + appsettings

1. Add `Session` section to `appsettings.json` (defaults: `MaxTurns: 20`, `SlidingExpirationMinutes: 30`)
2. Verify `appsettings.Development.json` does not override (leave absent — dev uses defaults)
3. **Stability note**: The section name `Session` and key names `MaxTurns` and `SlidingExpirationMinutes` are stable across patch and minor releases. Any rename constitutes a breaking change requiring a migration path.

### Phase E — Observability Validation

1. Run app via Aspire; send a two-turn chat sequence
2. Open Aspire dashboard → Traces: confirm `nexusops:session:*` Redis GET/SET operations appear as child spans
3. Confirm `session.created`, `session.history_loaded`, `session.history_saved`, and `session.degraded` appear in structured logs under their respective conditions (trigger a store-unavailable scenario to exercise the degraded event)
