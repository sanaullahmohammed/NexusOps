# Phase 0 Research: Order Investigation Saga Reliability Fix

## Decision 1: Root cause confirmation

**Decision**: The race is in `OrderInvestigationSaga.Initially(When(Requested))`, whose `.Publish(context => new BeginInvestigationFanOut(...))` call executes as part of the same pipeline as the state-machine transition, but — without a transactional outbox — MassTransit's EF Core saga repository sends that publish to the broker independently of, and not gated behind, the repository's own `SaveChanges()`/`INSERT` commit for the new saga row.

**Rationale**: Confirmed empirically, twice, via `NexusOps.IntegrationTests` against real RabbitMQ and PostgreSQL: the Postgres SQL command log shows `InventoryFinding`/`ProductFinding` columns being written on the saga row (proving `InventoryFindingReported`/`ProductFindingReported` were correctly correlated and consumed), while `OrderFinding` is never written in either run — grepping the full SQL trace for `"OrderFinding" = @` returns zero matches across two independent investigation attempts. This is consistent with, and only consistent with, `OrderFindingReported` arriving and being discarded by `OnMissingInstance(m => m.Discard())` before the row exists: `InvestigationFanOutConsumer.Consume` looks up the order first (a single sequential call) and publishes its result immediately, before it even begins the inventory/product calls — so among the three findings, `OrderFindingReported` is structurally the earliest to come back, and therefore the one most likely to race ahead of a same-request `INSERT` that has not yet committed. Inventory/Product's findings arrive later (after their own network round trip, which runs in parallel after the order leg completes), by which point the row has had enough time to commit.

**Alternatives considered**: A logging/telemetry gap (i.e., the write happened but wasn't logged) was ruled out — EF Core command logging is verbose and unconditional in this project's configuration, and it does show every other write (including retried ones after a `DbUpdateConcurrencyException`); an `OrderFinding` write, had it occurred, would appear in the same trace. Cross-test interference was also ruled out as the sole cause: the same failure reproduced identically after eliminating a separate, confirmed test-authoring bug (accidental parallel test execution), across two independent full runs.

## Decision 2: Fix mechanism — transactional EF Core outbox

**Decision**: Add a receive-endpoint-scoped MassTransit transactional EF Core outbox (`UseEntityFrameworkOutbox<OrderInvestigationDbContext>`) to `OrderInvestigationSagaState`'s receive endpoint, so that any message published while consuming on that endpoint — specifically `Publish(BeginInvestigationFanOut)` from `Initially(When(Requested))` — is held in an `OutboxMessage` row inside the *same* database transaction as the saga's own `SaveChanges()`, and only actually delivered to the broker after that transaction commits.

**Rationale**: This is not a novel mechanism for this codebase — `OrderActionSaga` (feature 006) already hit the identical class of problem for its own `Initially(When(...))` handler's `Publish(BeginOrderActionExecution)` and was fixed exactly this way (`NexusOps.WorkflowOrchestrator/Program.cs`'s `ReceiveEndpoint("OrderActionSagaState", ...)` block, `OrderAction/ServiceCollectionExtensions.cs`'s `AddEntityFrameworkOutbox<OrderActionDbContext>(o => { o.UsePostgres(); o.UseBusOutbox(); })`). Feature 005's own `plan.md` "Open Questions" table explicitly flagged the missing outbox as an accepted gap at the time, framed around retry-driven duplicate `CorrelationId`s rather than this specific ordering race — but the fix for both concerns is the same mechanism, so closing it now closes both.

**Alternatives considered**:
- *Add a small delay before publishing*: rejected — timing-based fixes are inherently flaky and don't provide an actual guarantee, only a probabilistic one; this is exactly the kind of fix that would pass locally and fail again under different latency conditions (as this bug itself demonstrates).
- *Change `OnMissingInstance` to retry/requeue instead of discard for the `Requested`-adjacent events*: rejected — this shifts the race to "how many retries is enough," doesn't fix the root cause, adds latency to the common case, and diverges from the precedent `OrderActionSaga` already set for the identical problem.
- *Make the fan-out consumer wait for the saga's row to be confirmed persisted before calling `GetOrderFindingAsync`*: rejected — there's no clean, race-free way for a separate consumer to observe "the saga's SaveChanges has committed" without itself depending on some other synchronization primitive; the outbox is the tool designed for exactly this "publish should not be visible before my own commit" guarantee.

## Decision 3: Scope of the outbox — `OrderInvestigationSagaState`'s endpoint only

**Decision**: Only `OrderInvestigationSagaState`'s receive endpoint is reconfigured to carry the outbox (mirroring `OrderActionSagaState`'s existing carve-out in `Program.cs`, via a scoped `Exclude<OrderInvestigationSagaState>()` on the generic `ConfigureEndpoints` sweep plus a manual `ReceiveEndpoint(...)` block). `InvestigationFanOutConsumer`'s own endpoint is untouched.

**Rationale**: The race is specifically about the saga's own state-commit-then-publish ordering; `InvestigationFanOutConsumer` doesn't own persisted state of its own; there is nothing there to protect. Matches `OrderActionSaga`'s precedent exactly, where only the saga's own endpoint (not `OrderActionValidationConsumer`'s or `OrderActionExecutionConsumer`'s) carries the outbox.

## Decision 4: Migration strategy — revised during implementation

**Decision (as actually implemented, superseding the original plan below)**: `OrderInvestigationDbContext` is configured to use MassTransit's *default*, unqualified `InboxState`/`OutboxState`/`OutboxMessage` mapping — the same physical tables `OrderActionDbContext`'s migration (feature 006) already created in the `workfloworchestrator` database — rather than a private copy. The new EF Core migration added to `OrderInvestigationDbContext` (`AddTransactionalOutbox`) is structurally a no-op (empty `Up()`/`Down()`); it exists only so this context's own migration history reflects that its model now includes these entities, satisfying EF Core's model-vs-database drift check for this context without attempting to re-create tables that already exist.

**Rationale (why the original plan below does not work)**: A private copy was attempted twice and rejected both times, empirically, against real Postgres:
1. **Renamed table** (`AddInboxStateEntity(b => b.ToTable("InvestigationInboxState"))`): normal EF Core operations (inserts, updates via `SaveChanges`) correctly used the renamed table, but MassTransit's Postgres row-lock statement provider — used for its `SELECT ... FOR UPDATE` inbox-dedup check — generates that specific query against a literal, unqualified `"InboxState"` string it derives independently of the entity's actual configured table name. That query silently matched `OrderActionDbContext`'s own (default-named) `InboxState` table instead, found no row there (since the real insert went to the renamed table), and retried the insert, which then hit the renamed table's own unique constraint — `duplicate key value violates unique constraint "AK_InvestigationInboxState_MessageId_ConsumerId"`, reproduced via `NexusOps.IntegrationTests` against real infrastructure.
2. **Renamed schema, default table name** (`AddInboxStateEntity(b => b.ToTable("InboxState", "investigation"))`): same failure mode — the row-lock query is *also* unqualified with respect to schema (no `investigation.` prefix), so it resolves via Postgres's `search_path` to the `public` schema's `InboxState` table (`OrderActionDbContext`'s) regardless of where the entity is actually mapped.

Both failures are visible directly in the captured Postgres SQL trace: the `INSERT INTO investigation."InboxState" (...)` (schema-qualified, correct) is immediately followed by `SELECT *, xmin FROM "InboxState" WHERE ... FOR UPDATE` (unqualified — the wrong table), then `System.InvalidOperationException: The instance of entity type 'InboxState' cannot be tracked because another instance with the same key value ... is already being tracked` on retry.

Once both contexts point at the *same* physical tables, this stops being a problem: the row-lock query's hardcoded, unqualified reference now correctly happens to be the *only* `InboxState` table in the default search path, so it finds exactly the row that was actually inserted. This is also architecturally coherent, not just a workaround: MassTransit's inbox dedup key is `(MessageId, ConsumerId)`, and `ConsumerId` already differs per receive endpoint (each saga's own endpoint gets its own), so a single shared outbox per physical database was always going to correctly isolate the two sagas' rows from each other regardless.

**Alternatives considered**: A private copy of the outbox tables per `DbContext` (the original plan, described above) — rejected for the reasons just given: it does not work with this version of MassTransit's Postgres outbox implementation, confirmed empirically, not merely a theoretical concern. Delaying/removing/queueing the fan-out publish some other way was reconsidered here too, and rejected for the same reasons already given in Decision 2 — this is strictly a migration/table-topology decision, not a re-opening of the mechanism decision.

## Decision 5: Migration idempotency and ordering — found in code review after the first green run

**Decision**: `OrderInvestigationDbContext`'s new migration (`AddTransactionalOutbox`) does not stay a bare no-op. Its `Up()` is written as `CREATE TABLE IF NOT EXISTS`/`CREATE INDEX IF NOT EXISTS` for the shared tables, and `Program.cs` runs `OrderActionDbContext`'s migration *before* `OrderInvestigationDbContext`'s.

**Rationale**: A bare no-op `Up()` (the first version of this migration) silently assumes `OrderActionDbContext`'s own migration always runs, and runs first, and continues to exist. None of those are guaranteed by anything the schema itself enforces: this project explicitly documents `OrderAction` as deletable (Constitution V's domain-pluggability precedent — "delete the folder and its one registration call"), and a rollback of feature 006 (`OrderActionDbContext`'s migration `Down()`) drops these tables outright. `CREATE TABLE/INDEX IF NOT EXISTS` closes the first two of those paths -- a fresh database, or `OrderAction` deleted before `OrderInvestigationDbContext`'s migrations ever run -- by making `OrderInvestigationDbContext`'s migration self-sufficient: it creates the tables itself if they're not already there. It does **not** close the third: a rollback of `OrderActionDbContext`'s migration *after* `OrderInvestigationDbContext`'s `AddTransactionalOutbox` has already been applied and recorded. EF Core migrations run once per recorded history entry, not on every `MigrateAsync()` call, so `OrderInvestigationDbContext` would still believe its outbox tables exist and never re-attempt the `CREATE TABLE IF NOT EXISTS` — reproducing this feature's exact original symptom (the investigation saga hangs forever) at the schema layer instead of the timing layer. Accepted as out of scope: rolling back an already-shipped, already-live-verified feature (006) out from under a running deployment is not a supported operation this project's own migration story handles for *any* saga today, and adding that support here would be solving a problem this feature was never asked to solve.

That said, `OrderActionDbContext`'s own migration (feature 006, out of scope to modify here) is *not* idempotent — a plain `CREATE TABLE`. With both contexts present today, whichever runs first legitimately creates the tables and the second's `IF NOT EXISTS` correctly no-ops; but if `OrderInvestigationDbContext` ran first, `OrderActionDbContext`'s own non-idempotent `CREATE TABLE` would then fail with "relation already exists" — reproduced live during this same review pass. `Program.cs` therefore runs `OrderActionDbContext`'s migration first, deterministically, so today's two-context reality and Decision 4's self-healing property both hold at once.

**Alternatives considered**: Leaving the no-op and documenting the OrderAction-must-run-first dependency in a comment only — rejected: an undocumented-in-code, comment-only invariant is exactly the kind of implicit coupling that got silently violated before (the original race this whole feature exists to fix), and "the comment says so" is not a real guarantee. Making `OrderActionDbContext`'s own migration idempotent too was considered, and rejected as out of scope: it's feature 006's already-shipped, already-live-verified code, and this feature's job is to fix `OrderInvestigationSaga`, not to re-touch `OrderActionSaga`.
